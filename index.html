Shield Engineering

The visual language for Shield Legal's operations software: modern, professional, and a little bit warm.
v0.9.0 · release candidateClose to 1.0. What is still open is listed under Accessibility conformance; how a change gets in is under How this guide changes.

Overview

What this is

The style guide for the software Shield Engineering builds. Engineers use it as the reference for colors, type, spacing and components, with the class and token names. Everyone else can use it to see why our products look the way they do.

Why it looks like this

Shield Legal delivers mass tort, personal injury and other legal-related data to law firms and their funding partners. Those relationships depend on precise, signed agreements, so the interface has to make status unmistakable and feel calm and trustworthy to people reviewing documents with legal weight.

Design principles

Modern, but professional. Clean type, generous spacing and soft rounded controls, with a tone suited to legal work. Legible first. Text and status colors are tuned for contrast, because misreading a term or a status is costly. Consistent. One set of tokens drives everything. Easy to change. Each visual decision lives in a named token or a short CSS rule.

Light mode

Modern and professional, with a hint of warmth. The page is a faint warm white (#FFFBF7), like the pages of a novel or an old legal pad, and cards stay pure white so content sits on the page like sheets of paper. Text is solid black, like ink. The warmth stays subtle so it never looks yellowed in a modern technical product.

Dark mode

Modern and technical, but not harsh. The goal is comfort: think of a well-lit night under a full moon, not a terminal. The page is a deep midnight blue (#0B1220) instead of black, cards sit just above it in a slightly lighter navy, and text is a warm off-white (#FFFBF7) that stays easy to read, so long sessions stay easy on the eyes. The guide follows the operating system's light or dark setting until a visitor picks one in the sidebar; products should do the same.

How it is built

Plain HTML, CSS and JavaScript, no UI framework and no build step. tokens.css holds the values (colors, fonts, spacing, radius, shadow, motion) and components.css holds the components that use them. shield.js adds the interactions on this page. Classes are prefixed shield-. Everything below is a working component: open the select, flip the switch, dismiss a tag, push a toast.

Engineers: switch on Engineer Mode at the top of the sidebar. A code panel appears at the end of each section with copy-paste HTML and the tokens involved.

Beyond components: Writing and Data formats say how words, dates and numbers are shaped; Page patterns says how a whole screen is put together; Accessibility conformance is the WCAG 2.2 AA statement for everything here; and How this guide changes is the contract for changing it.

Typography

Headings and the brand mark use Fraunces, a soft serif with a book-like, editorial voice that nods to printed legal documents. Body text and every control use Satoshi, a clean modern sans-serif that stays clear at small sizes. Both are variable fonts hosted in the fonts/ folder, so nothing depends on a network request. If they fail to load, headings fall back to Georgia and body text to the system sans-serif.

Four sizes cover body copy and everything inside the components. 16px is the base because 14px is too small for most people to read comfortably for long. Change a number in tokens.css to resize that role everywhere.

Small text: --weight-small

Satoshi looks light at small sizes, so small text and control labels (buttons, tabs, menu items, tags, table cells, captions, alerts, toasts, step titles, stat labels) use --weight-small (500) instead of 400. Paragraphs and typed input text stay at 400. Change that one token to adjust all of it.

Motion

Motion tells people that something changed: a button reacted, a menu opened, a message arrived. In Shield products it is small and fast. Pick a duration by what is changing, never by what feels nice: there are four durations, two easings, and a rule for when to use each.

How to use it

  1. Something small changes in place (hover, focus, checked, a chevron turning): --duration-fast with --ease-standard.
  2. Something appears (modal, toast, popover, drawer): --duration-base. Use --ease (fast start, soft landing) for things that slide in, --ease-standard for things that fade in.
  3. Something leaves. Components here hide without an animation. If you add one, make it shorter than the way in: --duration-fast.
  4. Animate only color, background-color, border-color, opacity, box-shadow and transform. Do not animate width, height, margin, top or left: neighbors jump.
  5. Never make anyone wait. Nothing should be disabled or hidden while an animation plays. Nothing should take longer than --duration-slow (0.25s).
  6. Never type a number. Write var(--duration-fast), not 0.15s.
  7. Reduced motion is automatic. People who ask their OS for less motion get near-instant transitions from tokens.css; never override it.

Sizes

Icons come in five heights. Pick the height from this scale and let the width follow the glyph's own ratio (a 448-wide glyph at height 16 is 14 wide), so every icon on a row shares a height and none is stretched. Icons sit centered on the text line, not on the baseline. Anything clickable has a hit area of at least 24 by 24 px (WCAG 2.2 SC 2.5.8), 44 px where touch is expected: add padding to the button, never scale the glyph.

Writing

Words are part of the interface. A label one word too long, an error that scolds, a date that reads two ways: each one costs a person who is reviewing documents with legal weight. These rules apply to everything a product shows, from a button to a notification email. The copy on this page follows them, and the review for a new screen checks them.

Voice

  • Plain, direct, calm. Short sentences, active voice, present tense. Say what happens, not how the system feels about it. No exclamation marks.
  • Talk to the person. "You" for the reader, "we" for Shield. Instructions are imperative ("Choose a catalog"); completed actions are past tense ("Offer sent").
  • Use the word the agreement uses. A partner group is not a client, an offer is not an order, a change request is not an edit. The glossary below is the list; add to it rather than inventing a synonym.
  • Never blame, never apologize. "The file is larger than 25 MB", not "You uploaded a file that is too large". No "please", "sorry" or "oops".

Capitalization

Sentence case everywhere: headings, titles, labels, buttons, menu items, tabs, tags and table headers. Capitalize the first word and proper nouns (Shield, Fraunces, Harlow & Vance) and nothing else. No Title Case and no typed capitals: the small uppercase table headers and group labels on this page are produced by CSS from sentence-case text, so screen readers hear words rather than letters and the style can change without touching content.

Partner groupsPartner Groups · PARTNER GROUPS

Exception: a legal or product name that is a proper noun keeps its own capitals (Harlow & Vance, Shield Engineering). The StatusTag words in Tag & pill are sentence case for the same reason: "Partner signature", not "Partner Signature".

Buttons and labels

  • A button starts with a verb and names the object: "Onboard partner group", "Create change request", "Export as PDF". Universally understood single words stay single: Save, Cancel, Close, Delete, Done.
  • No articles in buttons, labels or headings: "Add product", not "Add a product".
  • Never "Click here", "Submit" or "OK" for anything with a consequence. The label says what will happen, so a person can decide from the button alone.
  • One Primary per screen (Button). A Danger button is red because it destroys something that is hard to undo; its label still names what it destroys ("Delete partner group"), and the red is never the only signal.
  • Field labels are nouns, two or three words, no colon: "Effective date", "Primary contact email". The hint under the field, not the label, carries the format or the example.
  • Mark the minority. On a form where most fields are required, mark optional ones "(optional)" in the label; on a form where most are optional, mark the required ones with the asterisk. Use one convention across the product. This guide's forms are mostly required, so they use the asterisk.

Errors

An error message has three parts: what stopped, why, and what to do. For a single field, "what to do" is the whole message: tell the person what to enter. For a page or an action, a title of three or four words names what stopped, then one or two sentences give the reason, the action to take and what happens if nothing is done. An error the person must act on is never only a toast; it is an Alert or a Modal.

  • Words not used in an error: please, sorry, oops, valid, invalid, forbidden, illegal, and codes a person cannot act on (keep the code on a copyable detail line for support).
  • Keep what the person typed. Never clear a field to show an error.
  • Check when they leave the field and again on submit, not on every keystroke (Form layout); on submit, the error Alert at the top lists every problem and links to the field.
  • Same words everywhere: the inline message, the summary and the announcement to a screen reader use one sentence, not three.

Punctuation

  • Full sentences end with a period: body copy, hints, alert bodies, empty-state descriptions. Headings, titles, labels, buttons, tooltips, menu items and table cells do not.
  • No colon at the end of a heading or a label. One space after a period.
  • Use the real characters: an ellipsis (…) not three periods, an en dash (–) in ranges, a minus sign (−) for negatives, a multiplication sign (×) for dimensions, curly quotes in prose.
  • Ampersand only inside a name that uses it (Harlow & Vance) and in a section title where space is tight; "and" in sentences.

Numbers, money and abbreviations

  • Numerals in the interface ("3 waiting", not "three waiting"), commas from four digits (1,024), a leading zero before a decimal (0.5). The full rules, with dates and currency, are in Data formats.
  • Spell an abbreviation out on first use unless everyone knows it (PDF, NDA, ID, UTC). No periods in abbreviations. Months and days are full words in prose and three letters without a period where space is tight (Sep, Mon).
  • "Percent" is the symbol with a numeral (34%); a change in a percentage is in points (+2 points), never "+2%".

Data formats

Shield records are evidence: when an offer was signed, how much an order is worth, which partner group an identifier belongs to. A value that can be read two ways is a defect, not a style choice. These rules give every kind of value one shape, and one place in code that produces it: the browser's Intl formatters, which carry Unicode CLDR locale data, with the product locale and the record's time zone passed in. Nobody builds a date string by hand.

In code

  • Store and send ISO 8601 in UTC (2026-09-12T13:04:00Z) and format at the edge, in the person's locale and the record's IANA time zone.
  • Format through Intl, never by concatenation. The browser carries the locale data, so month names, separators and AM/PM are right without a library.
  • Put the machine value in <time datetime> so a column can sort on it, a person can copy it, and a screen reader can read it.
const when = new Date("2026-09-12T13:04:00Z");
new Intl.DateTimeFormat("en-US", { dateStyle: "medium", timeStyle: "short",
  timeZone: "America/New_York", timeZoneName: "short" }).format(when);   // "Sep 12, 2026, 9:04 AM EDT"
new Intl.DateTimeFormat("en-US", { dateStyle: "medium" }).format(when);   // "Sep 12, 2026"
new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(48200);   // "$48,200.00"
new Intl.NumberFormat("en-US", { notation: "compact" }).format(1250000);                // "1.3M" (tiles only)

Page patterns

Components say what a button or a table looks like. Patterns say how a whole screen is put together, so two engineers building two list pages produce the same page. Three patterns cover nearly every screen in Shield's operations software: the page header every page starts with, the list page, and the record page. Each also says what the screen shows while it loads, when it is empty, and when something has gone wrong.

Page header

Every full page opens the same way: a breadcrumb when the page is two or more levels deep; the page title as the page's only h1, kept to one line (the full text goes in title when it truncates); an optional info icon for the one sentence that explains the page; and the page actions right-aligned, with at most one Primary. A record page adds up to four key facts under the title: the status as a Tag, and the three values a person needs before reading further. Tabs, if the page has them, sit directly below the header.

Date picker

A date field is the browser's own date input styled as a normal text field. That keeps it fully keyboard and screen-reader friendly, shows the calendar in the visitor's language and format, and costs nothing to maintain. Type the date, use the arrow keys, or open the calendar from the icon. Say the expected format in the hint when typing matters, and use two fields for a range.

What it is and how to get it

The native HTML date input, <input type="date">. It is built into every browser, so there is nothing to install: add the element and the shield-input class. The calendar popup is drawn by the browser, so it looks different from browser to browser and cannot be restyled. People see the date as MM/DD/YYYY (US browsers follow the visitor's language settings). Your code reads and writes the value as YYYY-MM-DD, which follows the ISO 8601 standard (as HTML uses it) and is how the element passes it along, not what is shown on screen. It is a plain calendar date with no time or time zone.

Form layout

  • Label above the field, always visible. A placeholder is an example, not a label.
  • Required fields get a red asterisk before the label.
  • Help text goes under the field, short.
  • Check a field when the person leaves it and again on submit, not on every keystroke.
  • Errors: the field border turns red, a red icon marks the field, and the message appears in text directly under the field, with a hidden "Error:" prefix for screen readers. It says what to enter ("Enter a date after the effective date"), never "invalid", "please", "sorry" or a code. Hover is never the only way to read it. Keep what the person typed.

  • Never ask twice. In a multi-step flow, anything the person already entered is filled in or offered for selection, not typed again (WCAG 2.2 SC 3.3.7).
  • Buttons: primary action on the right, Cancel beside it.

Toast

A brief confirmation, for example "Saved". Pushed from code with sgPushToast() (or your framework's equivalent), shown top-center, and gone after 3 seconds. The stack is a polite live region, so screen readers hear each toast without losing their place. Accessibility conformance

Shield products meet the W3C Web Content Accessibility Guidelines (WCAG) 2.2 at Level AA, and every component follows the WAI-ARIA Authoring Practices Guide (APG) pattern for its role. This is the conformance statement for the guide itself: which criteria matter for a component library, how each is met, and what is still open. Met means the demos on this page do it and a rule or tools/check.mjs keeps it true. Open means the guide knows and has not yet decided. A product screen built from these components inherits the "met" rows and still has to be checked as a whole (the checklist below).

Review checklist for a screen

Before a screen built from these components ships, someone who did not build it goes through this list. It is Nielsen's ten heuristics in Shield's words, plus the mechanical checks.

  1. Status is visible. The person can always tell what state the record is in and what the system is doing (a Tag, a skeleton, a spinner, a toast).
  2. Words match the work. Terms come from the glossary; dates and amounts follow Data formats.
  3. There is a way back. Cancel closes without saving, destructive actions confirm, nothing is lost on a mistake.
  4. It looks like the rest of Shield. One Primary, the page pattern it belongs to, the status components it should use.
  5. Mistakes are prevented before they are reported: formats in hints, disabled until valid, type-to-confirm.
  6. Nothing has to be remembered from another screen: key facts in the header, values filled in rather than asked again.
  7. Experts can go fast: keyboard for everything, bulk actions, search.
  8. Nothing is there that does not earn its place.
  9. Errors say what to do, in text, next to the problem, in the words from Writing.
  10. Help is where it always is: the info icon by the title, the support link in the top bar.
  11. Mechanical: node tools/check.mjs passes; Tab through the whole screen; read it with a screen reader once; switch to dark mode; turn on the OS "Increase contrast" and "Reduce motion" settings; resize to 320px.

How this guide changes

A style guide that cannot change is ignored; one that changes without warning breaks products. This section is the contract: who owns the guide, how a change is proposed and approved, how versions are numbered, how something is retired, and what 1.0 means. The short version for a pull request is CONTRIBUTING.md in the repository.

Who

RoleDoes
OwnerKeeps the guide coherent: merges, releases, writes the changelog, says no. One named person, listed in .github/CODEOWNERS once the repository is under the organization.
Design reviewerApproves that a rule is the right rule for Shield: it fits the principles in the Overview and the people reviewing documents with legal weight.
Engineering reviewerApproves that the rule can be built as written, the check passes, and the demo and snippet match.
Product teamsConsume the guide: pin a version, read the changelog on upgrade, and open an issue when a screen needs something the guide does not have. They do not fork a component locally.

Proposing a change

Kind of changePathApprovals
A wording fix, a comment, a typoPull request.One (the owner or either reviewer).
A new value, component, modifier, pattern or sectionAn issue first: the problem, where it shows up in a product, the proposed rule, and the sources it rests on. Then a pull request with the demo, the snippet, the tokens, the copy and a changelog line.Two: design and engineering.
A rename or removal of a token, class or ruleThe deprecation path below. It is announced in a minor release and lands in the next major.Two, plus the owner.

Every pull request: node tools/check.mjs passes; both themes were looked at; the demo in index.html and the entry in snippets.js agree; any copy that quotes a number was updated; a line was added under Unreleased in CHANGELOG.md; a new rule ends with a Sources list like the ones on this page.

Versions

The guide follows semantic versioning. The number lives in one place, SG_VERSION in shield.js, and is stamped into the sidebar, the cover and the footer; the check fails if it and the newest changelog entry disagree. Each release is a git tag vX.Y.Z.

BumpWhenExample
Patch (0.9.0 → 0.9.1)Copy, comments, a fix that changes no token value, class name or behavior a product depends on.Correcting a contrast figure in the Color caption.
Minor (0.9.0 → 0.10.0)A new component, token, modifier, pattern or section. Everything that existed keeps working.Adding the Status display table; adding --brand-fill.
Major (0.x → 1.0.0, 1.x → 2.0.0)A token or class is renamed or removed, or a value changes in a way products must react to: a spacing step, a breakpoint, the primary fill.Moving Primary from blue-7 to blue-8 would have been a major after 1.0; before 1.0 it is a minor with a loud changelog entry.

Retiring something

  1. Mark it deprecated in a minor release: a comment on the rule ("Deprecated in 0.10, use --brand-fill"), a note in the guide beside the demo, and a line under Deprecated in the changelog that names the replacement.
  2. Keep it working for at least one minor release, so a product team can upgrade and migrate on its own schedule.
  3. Remove it in the next major, with the migration written in the changelog (old name → new name, and why). Where it can be done with a search and replace, say so.

The guide has done this informally before: .convert / .bad became .positive / .negative, and the blue-7 fills became --brand-fill in 0.9. From here on it is written down.

Releases

While the guide is 0.y.z, a minor release goes out every two weeks if there is anything to ship, and a patch any time. After 1.0, a minor goes out monthly and a major no more than once a year, announced at least a month ahead with its migration notes. A release is the tag, the changelog entry and the stamped version; nothing else needs to be built. The GitHub Action runs the check on every push, so the main branch is always releasable.

What 1.0 means

  • Every Open row in Accessibility conformance is decided.
  • The brand assets listed under Logo & brand exist.
  • The glossary is confirmed against the product's data model.
  • The React components in Shield's products read tokens.css (or the tokens.json export) directly, and this guide renders those same components, so the guide and the product cannot drift apart.
  • Two real product screens have been built from Page patterns and reviewed with the checklist.
  • The repository lives under the organization, with CODEOWNERS and the check required to merge.

Where the tokens live

tokens.css is the source of truth and has three tiers. The palette (--blue-1 to --blue-10) is never read by a component. The role and alias tokens (--brand-fill, --text-secondary, --error-bg, --space-4) are the public API: components and products read these, and choose them by meaning, never because the color happens to match, or dark mode breaks. Component-specific values are local rules in components.css. node tools/export-tokens.mjs writes the same tokens to tokens.json in the Design Tokens Community Group format, so design tools and other platforms read the values the browser reads.
